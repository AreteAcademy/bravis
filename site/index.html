Eficiência medida

Velocidade não é adjetivo. É número.

Em Kubernetes, tudo que sobra na imagem é baixado por todo nó que rodar aquele passo. Por isso as imagens são por papel, não por projeto.

5,8MB

Imagem de um passo em Go — contra 1,87 GB da imagem única que fazia tudo.

0,18s

Partida a frio do pod em Go. Python: 0,54 s. dbt: 3,3 s.

2,68s

Economizados por pod de dbt, com o parse já embutido na imagem.

1binário

Transformação, orquestração, fila, scheduler e UI. Sem dependência externa.

Medições e método em docs/IMAGENS.md

Um pod por passo

Não existe worker genérico esperando trabalho.

Um worker monolítico obriga a imagem a conter tudo que qualquer passo possa precisar. No Bravis, o pod sobe com a imagem exata daquele passo e um comando — e desaparece quando termina.

Comparação entre imagem única e um pod por passo
Situação Imagem única Um pod por passo
Passo de dbt 1,9 GB · 1Gi de RAM 1,9 GB · 1Gi de RAM
Fetcher em Go ao lado 1,9 GB · 1Gi de RAM 12 MB · 32Mi de RAM
Trocar a versão do dbt Rebuild de tudo Uma linha no YAML daquele workflow
Um passo que vaza memória Derruba o worker e os vizinhos Morre sozinho

O que você deixa de pagar

  • Uma imagem de 1,87 GB baixada por todo nó, para rodar um fetcher de 12 MB.
  • Subir o dbt de 1.10 para 1.11 em todos os pipelines de uma vez.
  • Pico de memória do maior passo virando o piso de todos os passos.

O que passa a valer

  • Isolamento total. Cada passo em seu container, sem contaminação de estado.
  • Escala horizontal. O cluster distribui os pods; o pico sobe e desce sozinho.
  • O mesmo arquivo roda local como processo, sem cluster nenhum.

Declarativo por padrão

Tudo é YAML. O que não é, é Go.

Workflow, agenda, dependências, recursos e parâmetros num arquivo versionável. Quando o trabalho é buscar e carregar dados, o SDK em Go entrega o fetcher inteiro em vinte linhas.

platform_workspace.yaml 
name: platform_workspace
schedule: "0 5 * * *"
concurrency: 1   # impede que um run se sobreponha

# Imagem padrão dos passos. Cada passo pode trocar a sua.
image: us-central1-docker.pkg.dev/zarv/apps/dbt:1.10.3
resources:
  cpu: 200m
  memory: 1Gi
  limits: {memory: 2Gi}

steps:
  - id: bronze_workspace
    run: dbt build --select bronze_workspace+

  - id: silver_workspace
    run: dbt build --select silver_workspace+
    depends_on: [bronze_workspace]

  # Outro runtime, outro tamanho: binário Go em distroless.
  - id: notificar
    image: ghcr.io/zarvhq/notify:0.3
    shell: false   # distroless não tem shell
    run: /notify --canal dados
    resources: {cpu: 25m, memory: 32Mi}
    depends_on: [silver_workspace]

type: chain é açúcar para a ordem do arquivo — o parser converte em arestas, e o motor conhece apenas DAG.

params — o que muda entre dois disparos 
params:
  - name: load_full
    type: boolean
    default: "false"

  - name: start_date
    type: string
    pattern: '^\d{4}-\d{2}-\d{2}$'

steps:
  - id: run
    run: dbt build --vars '{"load_full":"{{ .load_full }}"}'

# Um disparo agora, com o parâmetro trocado:
$ bravis run wf.yaml --param load_full=true

# Um mês inteiro, mesmo parâmetro:
$ bravis backfill diario --from 2026-01-01 --to 2026-01-31 \
    --param load_full=true

Na UI, um workflow com params ganha formulário no lugar do botão simples. Sem editar arquivo para trocar um disparo.

main.go — um fetcher inteiro 
package main

import (
    "time"

    "github.com/AreteAcademy/bravis/sdk"
)

func main() {
    sdk.Run(sdk.Pipeline{
        Source: sdk.Source{
            URL:     "https://api.example.com/v1/events",
            Timeout: 15 * time.Second,
            Guard:   sdk.RejectIf("error"),
            Expand:  sdk.ArrayAt("results"),
        },
        Target: sdk.Target{
            Provider: "example",
            Entity:   "events",
            Key:      sdk.Key("id"),
            When:     sdk.Field("created_at"),
        },
    })
}

Flags, -dry-run, logging, retry, paginação, procedência, criação de tabela e código de saída vêm do sdk.Run. O que sobra no arquivo é só o que é específico daquela fonte.

bash 
# Schema: subcomando próprio, porque `serve` nunca altera schema.
$ bravis migrate up

# API + UI server-rendered, com a DAG ao vivo.
$ bravis serve
  ouvindo em :8080

# O outro laço: materializa slots da agenda e executa a fila.
$ bravis scheduler --interval 5s --concurrency 4

# Liveness não consulta o banco. Readiness consulta, e nomeia
# a dependência que falhou.
$ curl -s localhost:8080/health
  {"status":"ok"}

Liveness que depende de serviço externo faz o Kubernetes matar o pod quando o banco oscila, em vez de apenas tirá-lo do balanceador. Por isso /health e /ready são separados.

chain ou dag

type: chain segue a ordem do arquivo. type: dag usa depends_on — e passos irmãos rodam em paralelo.

agenda e backfill

Cron no próprio arquivo. concurrency: 1 impede que um */15 se sobreponha a si mesmo. Backfill de um mês num comando.

validado na CI

A validação de workflow não precisa de banco, então roda na pipeline junto com os testes — antes de qualquer coisa chegar ao cluster.

mesmo arquivo, dois lugares

Local, cada passo é um processo. No cluster, cada passo é um pod. O YAML não muda entre os dois.

Arquitetura

Dois laços independentes.

O scheduler cria os runs. A fila os executa. Separar os dois significa que um pode cair sem afetar o outro — e que reprocessar não depende do relógio.

Pending → Running → Succeeded. O pod é criado, acompanhado, o log é seguido, o exit code é lido — e o pod desaparece.

Recursos

A stack inteira, num artefato.

Nada aqui é plugin, sidecar ou serviço à parte. É o mesmo binário, com o subcomando que o papel exige.

Binário único

Escrito em Go, sem runtime para instalar. Roda em Kubernetes, em Docker ou direto na sua máquina — o mesmo artefato nos três.

Workflows em YAML

Declarativo, versionável e legível por gente. Revisão de pipeline vira revisão de diff, não uma sessão de cliques na UI.

Kubernetes-nativo

Cada passo vira um pod com a imagem, o comando e os recursos que ele declarou. Seu runtime, seu limite, sua responsabilidade.

Scheduler e fila

Dois laços independentes: cron, backfill e retry automático. Um cai, o outro segue — e a fila é persistente, não memória de processo.

UI server-rendered

Overview com métricas e gráficos, busca e filtros nos workflows, pausar e executar, e a DAG com o estado de cada passo ao vivo.

Imagens por papel

Go, Python e dbt em imagens separadas, cada uma com o mínimo do seu papel — em vez de um monólito de 1,87 GB para todos.

SDK em Go

Extração HTTP com retry, timeout, guard e paginação (header Link, cursor, offset) e carga em lote no BigQuery.

Offline por desenho

Fontes e bundles são servidos do próprio binário. A UI funciona num cluster sem saída para a internet.

Primeiros passos

Do zero à DAG ao vivo.

Precisa de um PostgreSQL e da variável BRAVIS_DATABASE_URL. O resto está dentro do binário.

Instalar

Um go install, ou a imagem pronta se preferir container.

$ go install github.com/AreteAcademy/bravis/cmd/bravis@latest

Aplicar o schema

Migrations embutidas, em subcomando próprio — serve nunca altera schema.

$ bravis migrate up

Subir a UI

API e interface no mesmo processo, em :8080.

$ bravis serve

Ligar o scheduler

O segundo laço: materializa a agenda e executa a fila.

$ bravis scheduler --interval 5s --concurrency 4
