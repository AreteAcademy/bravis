All configuration comes from the **environment**, read once at boot. Nothing
consults the environment afterwards: a process whose configuration changes
mid-run is a process whose behaviour nobody can reproduce.

## Required

| variable | |
|---|---|
| `BREVIS_DATABASE_URL` | Postgres. Missing = **boot error** in the five subcommands that use the database |

## Process

| variable | default | |
|---|---|---|
| `BREVIS_ENV` | `local` | `local` logs in text and leaves the interface open; anything else requires credentials and logs JSON |
| `BREVIS_HTTP_ADDR` | `:8080` | listen address |
| `BREVIS_LOG_LEVEL` | `info` | |
| `BREVIS_SHUTDOWN_TIMEOUT_SECONDS` | `15` | integer; a non-numeric value is a boot error |
| `BREVIS_BRAND_FILE` | `brand.yaml` | branding; absent = default |
| `BREVIS_UI_URL` | — | base of the run link in alerts |
| `BREVIS_SLACK_WEBHOOK` | — | destination for failure alerts. Empty = nobody is told |

## Authentication

| variable | |
|---|---|
| `BREVIS_AUTH_USUARIO` | interface user |
| `BREVIS_AUTH_SENHA_HASH` | `pbkdf2-sha256$…` hash, generated by `brevis hash` |
| `BREVIS_AUTH_SEGREDO` | 32+ bytes to sign the session (`openssl rand -base64 48`) |

All three come together, or none does.

:::danger Half-configured is a boot error
Whoever filled in the username believes the door is closed. The interface
triggers pipelines: a `POST /workflows/<slug>/trigger` runs a `dbt build` that
writes to the warehouse. Open on the internet, it is a remote control for the
warehouse — and a log warning does not undo that belief, because nobody reads
the log of a process that works.
:::

Outside `BREVIS_ENV=local`, coming up without credentials is refused:

```
erro: BREVIS_ENV=production exige credencial: defina BREVIS_AUTH_USUARIO,
BREVIS_AUTH_SENHA_HASH (gere com `brevis hash`) e BREVIS_AUTH_SEGREDO
```

## Task environment

| variable | default | |
|---|---|---|
| `BREVIS_TASK_ENV` | empty | what each step receives |

A task does **not** inherit the orchestrator's environment. The reason is
concrete: the process carries `BREVIS_DATABASE_URL` with the Postgres username
and password, and a workflow is an arbitrary command written by someone else —
inheriting would hand the database credentials to every step of every pipeline.

What the task needs is declared:

```bash
BREVIS_TASK_ENV=GOOGLE_PROJECT_ID,STAGE   # forwards these two from the process
BREVIS_TASK_ENV=STAGE=prod                # sets a literal
BREVIS_TASK_ENV='*'                       # forwards everything EXCEPT BREVIS_*
```

`PATH` and `HOME` are always included — without `PATH` no command resolves, and
the error would be a "not found" that explains nothing.

A missing name does **not** become an empty string: `GOOGLE_PROJECT_ID=""` would
make dbt fail with a worse message than a missing variable.

## Kubernetes

**Installation** decisions, not workflow ones.

| variable | default | format |
|---|---|---|
| `BREVIS_PODS` | `auto` | `auto`, `on` or `off`; anything else is a boot error |
| `BREVIS_POD_NAMESPACE` | the cluster's | |
| `BREVIS_POD_SERVICE_ACCOUNT` | — | |
| `BREVIS_POD_PULL_SECRETS` | — | comma-separated list |
| `BREVIS_POD_ENV_FROM_SECRETS` | — | comma-separated list |
| `BREVIS_POD_ENV_FROM_CONFIGMAPS` | — | comma-separated list |
| `BREVIS_POD_ALLOWED_SECRETS` | — | comma-separated list |
| `BREVIS_POD_CREDENTIAL_PATH` | — | path mounted in the pod |
| `BREVIS_POD_CREDENTIAL_PVC` | — | PVC holding the credentials |
| `BREVIS_POD_NODE_SELECTOR` | — | `key=value,other=value` |
| `BREVIS_POD_TOLERATIONS` | — | `key=value:effect,…`; only the `Equal` operator |
| `BREVIS_POD_MANTER_EM_FALHA` | `false` | `true` keeps the pod for inspection |

In lists, empty entries are ignored: `a,,b` is a typo, and an empty secret name
would make the server reject the whole pod.

## Tests

| variable | |
|---|---|
| `BREVIS_TEST_DATABASE_URL` | database for integration tests; without it, they skip |

## Health endpoints

| | |
|---|---|
| `GET /health` | liveness — does **not** query the database |
| `GET /ready` | readiness — queries, and names the dependency that failed |

The separation is deliberate: a liveness probe that depends on an external
service makes Kubernetes **kill the pod** when the database wobbles, instead of
merely removing it from the load balancer.

## A complete example

```bash
# required
export BREVIS_DATABASE_URL='postgres://brevis:secret@db:5432/brevis?sslmode=require'

# production requires credentials
export BREVIS_ENV=production
export BREVIS_AUTH_USUARIO=operator
export BREVIS_AUTH_SENHA_HASH="$(brevis hash < password.txt)"
export BREVIS_AUTH_SEGREDO="$(openssl rand -base64 48)"

# what the tasks need, and nothing more
export BREVIS_TASK_ENV=GOOGLE_PROJECT_ID,STAGE,DBT_KEYFILE

# pods
export BREVIS_PODS=on
export BREVIS_POD_NAMESPACE=data
export BREVIS_POD_SERVICE_ACCOUNT=brevis-runner
export BREVIS_POD_ENV_FROM_SECRETS=bigquery-cred

# alerts
export BREVIS_SLACK_WEBHOOK='https://hooks.slack.com/services/...'
export BREVIS_UI_URL='https://brevis.example.com'
```
